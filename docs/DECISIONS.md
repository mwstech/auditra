# Decisions

Append-only. Every entry records a choice a future agent might be tempted to reverse, with the reason it must not be.

## Seeded from SPEC.md section 15

1. **Read-only is a product decision, not a limitation.** Do not add write tools "for convenience". A free tool connecting to production earns trust by being structurally incapable of breaking it.
2. **The server returns facts, never verdicts.** Do not add scoring, grading, or recommendation strings. The AI client does the judgment, so analysis improves without shipping plugin updates.
3. **Endpoint disabled by default.** Do not change to enabled for a smoother onboarding. Required posture for wp.org review and correct on its own merits.
4. **No Composer runtime dependencies.** Do not introduce a package to save fifty lines. WordPress ships everything needed, and a dependency-free plugin deploys as one rsync.
5. **Attribution confidence is always reported.** Do not drop the field to tidy the output. A guess presented as fact is worse than no answer.
6. **`sources_unavailable` is always reported.** Do not silently omit failed enrichment. A firewalled site must know its data is partial.
7. **No central hosted service.** Every install is self-contained. Near-zero marginal cost is what makes "free forever" honest.

## Phase 0

8. **Protocol versions supported: `2025-11-25`, `2025-06-18`, `2025-03-26`.** Verified against the live MCP specification on 2026-07-27; the latest version is `2025-11-25`, newer than the `2025-06-18` the spec document remembered. The server echoes the client's requested version when supported, otherwise returns `2025-11-25`. Plain `application/json` responses to POST are still explicitly permitted, and sessions remain optional, so the stateless no-SSE design stands.
9. **The token route pattern accepts any URL-safe token-shaped segment (`[A-Za-z0-9_-]+`), not strictly 64 hex characters.** A near-miss token must reach our handler and get a deliberate 401, not fall through to WordPress's generic REST 404. Do not "tighten" the pattern.
10. **JSON-RPC protocol errors on well-formed requests return HTTP 200 with an error object; only unparseable or structurally invalid bodies return HTTP 400.** This matches JSON-RPC-over-HTTP convention and the MCP transport spec's allowance. Do not convert method-not-found into an HTTP error status.
11. **Stray-output defense lives in the transport, in two parts.** An output buffer opens at `rest_api_init` for MCP requests, and all buffers are discarded in `rest_pre_serve_request` just before the JSON body is written. Other plugins do emit notices on REST requests; do not remove this because the local site happens to be clean.
12. **The local development site is a fresh WordPress install, not the planned clone of outsourcewebdesign.com.** Discovered during the Phase 0 survey on 2026-07-27. All test conditions from ENVIRONMENT-SETUP.md section 7 therefore come from `tests/seed-conditions.sh` until a real clone is imported. If a clone is imported later, re-run the survey before trusting seed assumptions.
13. **`composer.lock` is not committed.** Dev dependencies are two mature, stable packages (PHPCS, WPCS) resolved fresh in CI; a lock file in a dependency-free plugin repo invites noise PRs. Revisit only if CI ever breaks on a resolver change.

## Phase 1

14. **Token-in-path authentication is permanent; OAuth is off the table.** Confirmed working end-to-end on 2026-07-27: the connector is live in Claude Chat against `https://www.outsourcewebdesign.com` and `get_capabilities` returns correctly over public HTTPS. Do not build OAuth 2.1/PKCE "for completeness" — the swappable auth interface stays as insurance, nothing more.
15. **Tools are auto-discovered from `includes/mcp/tools/`.** Adding a tool means dropping one `class-tool-{name}.php` file there; the registry derives the class name from the file name and calls its static `register()`. Do not add a manual registration list that has to be kept in sync.
16. **`truncated` means rows were cut, never that a limit was clamped.** Confirmed with Benny after the Phase 1 checklist: a clamped limit shows as `limit` in the payload; `truncated: true` only when `returned < total`. A paginating client must be able to trust it.
17. **Detail mode caps at 10 rows per page; compact stays at default 25, max 100.** Detail mode is for looking closely at a handful of plugins, not for dumping the estate. The Phase 1 full-site detail response measured 19.3 KB with zero enrichment attached — the 20 KB budget has no headroom for Phase 3 without this cap.
18. **wordpress.org enrichment adds flags to rows, not numbers.** `abandoned`, `closed_on_wporg`, `untested_current_wp`, `no_wporg_record` go into the existing `flags` array on `list_plugins` rows — a few bytes each, and what the AI actually reasons over. The raw figures (install counts, ratings, support thread ratios, last-updated dates) live only in `get_plugin_details`, which is capped at five slugs. Anyone who wants the numbers is already drilling down. Do not add numeric wp.org fields to `list_plugins` rows.
19. **PHPCS standards are pinned to exact versions in composer.json** (php_codesniffer 3.13.5, wpcs 3.4.0) so local and CI can never resolve different rulesets. Bump both deliberately, together, in their own commit.

## Phase 2

20. **The capability taxonomy is deferred indefinitely.** The spec planned a curated JSON mapping ~500 slugs to capability categories and conflict pairs for Phase 6 redundancy detection. In the live Phase 1 connector test, the model detected a real sitemap conflict between All in One SEO and Google Sitemap Generator from plugin names alone — and correctly advised checking which sitemap Search Console reads before deactivating either. Better than a category lookup would have produced. Build Phase 6 without a taxonomy; revisit only if real audits show the model failing on plugins whose names give nothing away.
21. **Enrichment build order: endoflife (Phase 2) → vulnerabilities (Phase 3) → wordpress.org health (Phase 4).** Vulnerability matching moved ahead of wp.org health enrichment: on a live site, whether an active security plugin has a published CVE matters more than whether something looks abandoned. Site overview stays first because endoflife.date is the simplest API and the right place to prove the enrichment interface.

## Phase 3

22. **Two cache backends by design, and the split is deliberate.** Bulk enrichment (WPVulnerability now, wordpress.org in Phase 4) uses a single non-autoloaded option holding a keyed map of `{data, fetched_at}` with expiry checked in PHP. Options always hit the database, so persistence is guaranteed regardless of object cache state — a memory-only object cache must never turn 45 cache misses into 45 outbound calls per MCP request against a volunteer-run API. The endoflife client stays on transients: three or four keys with a seven-day TTL is exactly what transients are for. Do not "unify" these; the split is the point.
23. **Failed lookups are negative-cached for 15 minutes.** A down API must not be hammered on every request. Blocked-by-configuration (`WP_HTTP_BLOCK_EXTERNAL`) is not cached — configuration is not failure.
24. **The WPVulnerability core endpoint returns records pre-matched to the queried version; plugin and PHP endpoints return operator ranges to match locally.** Verified against the live API on 2026-07-27. Do not add operator matching to core findings — there is no operator to match — and never report plugin findings without version matching.

## Phase 4

25. **No `abandoned` flag. Mechanical flag names with documented thresholds only.** `abandoned` is an inference dressed as a fact — a plugin untouched for three years might be finished. The flags are `not_updated_2y` (>730 days), `not_updated_4y` (>1460 days, emitted instead of the 2y flag), `untested_current_wp`, `no_wporg_record`, and `closed_on_wporg`, each defined in `get_capabilities.flag_definitions`. The model calls something abandoned if it wants to; that is its job, not ours.
26. **`closed_on_wporg` exists because the API is unambiguous.** Verified live 2026-07-27: a closed plugin (display-widgets) returns HTTP 404 with `{"error":"closed","closed":true,"closed_date":"2021-01-30","reason":"security-issue"}`; an unknown slug returns 404 with `{"error":"Plugin not found."}`. Both are definitive answers and cache for the full TTL; only transport failures and unexpected shapes count as source-unavailable. `no_wporg_record` makes no claim beyond "not found" — premium, custom, renamed, and removed are not distinguishable.
27. **`untested_current_wp` is computed against endoflife.date's ordered WordPress release-cycle list** (three or more cycles behind the newest), not minor-version arithmetic, because arithmetic breaks across major boundaries (6.9 → 7.0). If the cycle list is unavailable the flag is simply not computed.
28. **Amendment to 18: raw wordpress.org figures may appear in `list_plugins` detail mode**, which is capped at 10 rows — the estate-dump risk that motivated 18 cannot occur there. Compact rows remain flags-only, permanently.

## Phase 5

29. **The prefix overrides file is not the deferred taxonomy.** Decision 20 deferred the *capability* taxonomy (slug → what the plugin does), and it stays deferred. `includes/data/prefix-overrides.json` is a different, smaller thing: slug → the option/table prefixes the plugin actually uses, for cases no algorithm derives (Contact Form 7 → `wpcf7_`). It is deliberately non-comprehensive — seeded with the plugins on the test site plus the most widely installed wp.org plugins — and grows through pull requests once the repo is public. Do not delete it citing decision 20, and do not grow it into a capability map.
30. **Attribution never guesses silently.** Every attributed row carries `high` (curated override), `medium` (prefix derived from the slug), and everything else lands in a visible unattributed bucket. Derived prefixes shorter than three characters or made of generic words (wp, all, my, ...) are never used — a wrong owner is worse than no owner. Core-owned options and cron hooks are matched by explicit exact-name lists, attributed to `wordpress-core`, never by pattern guessing.

## Phase 6

31. **No aggregate "site report" or deletion-history structure is added.** The Phase 5 live test confirmed the model reconstructs a site's deletion history from the three analyzers unprompted (orphaned tables + orphaned cron + unattributed autoload converged on the same deleted plugins). Same reasoning as decision 20: the server supplies facts, the client supplies the connections. Do not add a summarizing tool.
32. **`zero_content_usage` is narrow by design, and silent zeros are forbidden.** The flag means exactly: the plugin registers shortcodes, blocks, or post types, and none appear in content. A plugin registering no content features gets no flag and an explanation — it is not "unused", it is unmeasurable this way (hooks, filters, admin screens, REST, templates are all invisible to content scanning). A check that did not run returns null with a stated reason, never zero. A zero implying "safe to delete" about a load-bearing plugin is the single worst failure this product could produce.

## Phase 7

33. **The token is stored as a plaintext non-autoloaded option, deliberately.** What is stored: one 64-hex-character bearer token in `auditpress_token`, generated server-side from `random_bytes(32)`, never transmitted except inside the connection URL the admin copies. Why plaintext is acceptable: the token is a credential the site owner generates, owns, and can see — it is not a user password (nothing to protect from the site's own admin) and not a third-party secret (nothing another service trusts). The revoke path is one click: regeneration deletes and replaces the option and invalidates every existing connection immediately. What an attacker with database access gains: read-only access to plugin metadata through the MCP endpoint — strictly less than what the same attacker already has, since database access includes every post, user record, and password hash, and `wp_users` plus the salts mint working admin sessions. Hashing with display-once was considered and rejected: it would remove the settings page's ability to re-show the connection URL (the single thing every user must copy, sometimes twice), while defending against an attacker who has already won a strictly larger prize. This is the same posture WooCommerce and comparable plugins take with API credentials. Revisit only if the endpoint ever gains write capability, which decision 1 forbids.
34. **Failed external lookups back off progressively: 15 minutes, 1 hour, 6 hours, 24 hours, reset on any success.** A flat 15-minute retry is fine on one site and abusive at wordpress.org scale — thousands of installs hammering a broken volunteer-run API indefinitely is how a plugin gets blocked at the network level. The consecutive-failure count is stored with the negative-cache entry. The WPVulnerability outage of 2026-07-27 is the exact scenario.
35. **Multisite is not properly supported in v1, and says so.** The endpoint and collectors operate on the individual site they run on; network-wide aggregation does not exist. The conservative parts stay: settings and token management require `manage_network_options` on multisite so only network admins can expose data, and network-active plugins are detected in the inventory. Full multisite support (network admin page, per-site tokens, site-count-aware tools) is future work, not a v1 half-promise.

## Phase 8.5

36. **Two Plugin Check warnings stand as documented false positives.**
    - `PluginCheck.Security.DirectDB.UnescapedDBParameter` in `class-usage.php`: the batched counting query is assembled exclusively from fixed string literals and `%s` placeholders plus an integer loop-index alias; every caller value is bound through `$wpdb->prepare()`. The sniff cannot follow the assembly across the chunk loop. Re-verify by reading `count_patterns()` before assuming it is still safe.
    - `update_modification_detected: auto_update_plugin` in `class-inventory.php`: the plugin *reads* the `auto_update_plugins` option to report each plugin's auto-update setting. It never writes it and never hooks an update routine. Detection is name-based.
37. **Everything Plugin Check flags outside the shipped artifact is excluded by `.distignore`.** Running it against the working directory reports errors for `tests/`, `.github/`, `.claude/`, `docs/`, `deploy.sh`, and `phpcs.xml.dist`. The reviewed artifact is the zip: 32 files, 76 KB, **zero errors**. Always check the extracted zip, not the working tree.
38. **`admin/css`, `admin/js`, and `AuditPress_Token_Auth::revoke_token()` were removed as dead code.** No assets were ever enqueued (the settings page uses core admin markup and one inline script), and revocation happens through regeneration, not a separate call. `AuditPress_Autoload_Collector::autoload_values_in_use()` was also removed: it existed only to answer a one-off verification question in Phase 5.
39. **~~The name is AuditPress, slug `auditpress`. Final.~~ Superseded by 64.** The previous name was unshippable: wordpress.org's restricted-term list contains `plugin` as a bare entry, and Plugin Check's matcher treats bare entries as "cannot appear anywhere in the slug or display name" (only dash-suffixed entries are prefix-only matches). Every SPEC 2.1 fallback failed identically. `auditpress` was verified on 2026-07-27 by running Plugin Check's own matcher against its real 112-term list — `auditpress`, `audit`, and `press` each CLEAR — plus the official FAQ rules and an unregistered-slug check. Do not revisit the name; a further rename would invalidate the text domain, every prefix, the REST namespace, the repository, and the directory artwork.
40. **The audience is developers who already know what MCP is.** The readme description leads with "a read-only MCP server for WordPress" and the tool catalog, not with a protocol explainer. FAQ entries cover transport, authentication, and extension points rather than onboarding. **One deliberate exception: "The endpoint, stated plainly" is written for a wordpress.org reviewer with no MCP knowledge** — it has a different audience from the rest of the file and must stay self-contained and jargon-free. Do not "harmonize" its tone with the developer sections.

## Phase 8.6

41. **Upstream API data is never trusted for type.** A hostile or compromised upstream returning *valid JSON with wrong types* fatally crashed the endpoint during the Phase 8.6 audit: an array where a version string belongs reached `version_compare()`, which throws on non-scalar arguments. Every value taken from an external response is now `is_scalar()`-checked before use, and a bound that was present but unusable returns `unparsed` rather than `false` — ambiguous is never reported as clean. Do not remove these guards on the grounds that "the API returns strings"; that is exactly the assumption that broke.
42. **Vulnerability records are trimmed to the reported fields before caching.** The raw upstream payload carries advisory prose, CWE text, and SSVC blocks that are never surfaced; caching them whole put the persistent store at 1.4 MB for 89 entries (185 KB for a single popular plugin). Trimming to name, operator bounds, source identifiers, and CVSS score/severity cut that by ~80% (live site: 188 KB to 45.5 KB). Old untrimmed entries stay readable because the trimmed shape is a strict subset.
43. **Enrichment requests do not follow redirects.** Parallel fetching uses Requests directly, which bypasses `wp_safe_remote_get()`'s SSRF protections. The three hosts are hardcoded literals and none of them redirect in practice, so refusing redirects closes the only path by which a compromised upstream or hijacked DNS could aim the plugin at an internal address. `verify` is explicitly true.
44. **Concurrency is last-write-wins on three option-backed structures, and that is accepted.** The enrichment store, rate-limit buckets, and auth log are each read-modify-write without locking. Worst cases: a cache entry written by a concurrent request is overwritten and re-fetched at next use (costs one HTTP request, no corruption — each entry is written whole); two simultaneous bursts can each see a stale counter and admit a few extra requests past the per-minute limit (the limit is abuse-mitigation, not a security boundary, and the endpoint is token-authenticated anyway); a concurrent failed-auth pair can lose one log entry. No structure can be corrupted, because every write replaces a complete array rather than mutating a fragment. Locking would cost more than it buys.
45. **`pluginlens-test` and `pluginlens.local` are infrastructure names, not the plugin.** The Phase 8.6 rename changed the SSH host alias inside `deploy.sh`, pointing it at a host that does not exist; macOS's openrsync reports an unresolvable host as `io_read_buf`/`io_read_int` with child exit 255, which reads like a transport bug and cost real debugging time. `deploy.sh` now checks SSH reachability first and fails with a clear message. Do not rename either identifier when the plugin is renamed.
46. **`deploy.sh` stages the shipped file set before transferring.** It builds from `.distignore` — the same filter as the release zip — so the live site receives exactly the artifact wordpress.org would, and the transfer is 32 files rather than a 2,600-file tree. It verifies the remote file count after transfer instead of trusting rsync's exit code.
47. **The connection URL is built with `rest_url()` (a wrapper for `get_rest_url()`), never a hardcoded `/wp-json/` path.** Verified on plain permalinks: it correctly produces the `index.php?rest_route=/auditpress/v1/mcp/{token}` form, and the endpoint answers fully in that form — handshake, tools/list, tools/call. Do not hardcode the REST prefix; sites can move or disable it.
48. **Plain permalinks are supported, with a soft note rather than a hard requirement.** Because the query-string URL works at the HTTP level, the settings page shows an informational note only when `permalink_structure` is empty, telling the user what to do *if* their MCP client rejects the query string. Whether a given client's connector field accepts a query string is client-specific and untested by us; do not upgrade this to a blocking error without evidence.
49. **One activation notice, then silence.** The plugin is deliberately inert until enabled, which reads as broken. The notice appears after activation on admin screens only, is capability-checked and escaped, is suppressed on its own settings page, and self-clears permanently the moment the endpoint is enabled or the user dismisses it. Do not add recurring nags, upsells, or review prompts — guideline 11 and the product's posture both forbid it.
50. **The settings page offers the https:// connection URL even when `siteurl` is http://.** Discovered from a real connector failure on 2026-07-28: the live site stores `http://` but redirects to https, and the 301 **discards the POST body**, so the client reports "couldn't reach the server" rather than anything about a redirect — an unusually hard failure to diagnose from the client side. Since remote MCP clients require HTTPS regardless, the page now shows the https form with a warning explaining the swap, rather than handing the user a URL that cannot work. This is exactly the trap ENVIRONMENT-SETUP section 6 warned about; the product was walking users straight into it.

## Phase 8.7

51. **`check_vulnerabilities` declares one of four states, and the `not_performed` state returns no `findings` array at all.** The states are `complete`, `complete_stale`, `partial`, and `not_performed`. The reason for the fourth is structural rather than cosmetic: an empty `findings` array is *shaped like an answer* — it says "I looked and found nothing" even when nothing was looked at — and the coverage metadata that qualifies it sits beside it, where a reader or a model can skip it. A missing field cannot be skipped. When nothing could be checked, the response carries the state, the reason code, when the source last answered, and when a retry is due, and no findings container of any kind. The same rule applies wherever network-derived data is surfaced: `has_vulnerability` is absent on `list_plugins` rows that could not be checked (and those rows carry `vulnerability_unknown`, so absent never has to be read as "no"), and `get_plugin_details` omits `vulnerabilities` rather than emitting an empty array. Do not "simplify" this by always returning a findings array with a status field next to it; that is the exact shape this replaces.

52. **`_meta.sources_unavailable` (a flat array of names) was replaced by `_meta.sources`, one status object per source.** A name says something failed; it does not say what, and the responses differ completely: no outbound HTTP access is the site owner's firewall, an upstream error means wait, a timeout may be transient, an active backoff has a known retry time, and an unparseable response probably means the upstream schema changed and is worth reporting. Each source now carries `status` (`ok`, `stale`, `unavailable`), a `reason` code (`no_outbound_http`, `upstream_error`, `timeout`, `network_error`, `backoff_active`, `unparseable_response`, `oversized_response`, `serving_cached_data`), `last_success`, `next_retry` where a backoff window is open, and the data's age when it is stale. Facts only — no advice and no severity. This is a breaking schema change, taken deliberately before wordpress.org submission, while the plugin has no published consumers.

53. **Stale-while-unavailable, with a maximum staleness per source: 72 hours for vulnerability data, 30 days for wordpress.org and endoflife.date.** Before this, a failed lookup overwrote the cached payload with null, so a multi-week outage left the tool with nothing to say. A failure now increments a counter and leaves the last good payload in place; when the upstream is unreachable and the data is inside the staleness limit, it is served and explicitly labeled with its age and fetch timestamp. Fresh always wins — stale is a fallback after a fetch has been attempted and failed, never a shortcut past a cache miss. **72 hours** for vulnerability data because a three-day-old snapshot still contains every advisory older than three days (nearly all real exposure), because the escalating backoff tops out at 24 hours so reaching the limit means several consecutive daily retries have failed, and because past that point the chance of missing a newly published, actively exploited advisory stops being negligible and "we checked" becomes more misleading than "we could not check". **30 days** for the other two because a last-updated date, a tested-up-to value, and a release-cycle EOL date do not meaningfully move in a month. Store pruning was widened to 30 days and now keys off last-touched rather than last-fetched, so an entry failing daily is not pruned, which would reset its backoff and restart the hammering.

54. **Vulnerability responses are size-disciplined by bytes, not just by row count.** A neglected 45-plugin estate produced 171 findings and a 51 KB payload against the 20 KB budget in SPEC section 10. This was invisible for the whole build: every response during the upstream outage had an empty findings array. `check_vulnerabilities` now paginates (default 50, max 200), orders findings by published CVSS score so a truncated page is the most severe one, and enforces a hard 16 KB budget on the findings array that binds before the row cap. `get_plugin_details` caps at 10 findings per plugin with an honest total. Version strings from the upstream are truncated to 32 characters: they are ten characters at most in reality, and an uncapped one lands in `affected_range`, where a hostile upstream could use a 10,000-character version to crowd every real finding out of a byte-budgeted response.

55. **A second vulnerability provider is a seam, not a plan.** One outage with a known cause (a reserved-keyword collision on a database field) and a responsive maintainer is not a reliability pattern, and a second source would double the parsing surface, the failure modes, and the disagreement cases. What exists instead: `AuditPress_Vulnerability_Provider_Interface`, the `auditpress_vulnerability_provider` filter that every vulnerability-reporting tool resolves through, and the documented contract in CONTRIBUTING.md. Adding a provider is one file. Do not add one speculatively.

56. **All four published CVSS generations are read, and the `ne` operator is mapped.** Validated against the WPVulnerability OpenAPI 3.1 specification. The parser read `cvss3` then the legacy `cvss` block only, so a record scored solely under CVSS v4 or v2 lost its score and severity entirely — confirmed on real data (Advanced Custom Fields, CVE-2012-10025, published 10.0 critical under v4, previously reported with no severity at all). Precedence is `cvss3`, `cvss`, `cvss4`, `cvss2`, unchanged for the ~99% of records the first two cover, and a score taken from anything other than a v3 block is labeled with `cvss_generation` so v4 and v3 numbers are never silently compared. The schema's `ne` operator was also unmapped, which made any record using it `unparsed`. The `supplychain` block was implemented after this phase's first review; see 57.

57. **Supply-chain audits ship in 1.0.0, in their own array, never merged into the CVE findings.** The data was already in the response the parser fetched and discarded, and the matching engine was already built and verified, so reading it was a parser addition rather than a new integration — and the false negative it closes is the most damaging one this tool can produce: a plugin whose update channel was hijacked reporting as clean. Design constraints, each of which is load-bearing:

    - **Its own array and its own `type`.** A supply-chain audit says someone with publishing rights shipped code the author did not write. That is not a CVE, carries no CVSS, and sorting it into a CVSS-ordered findings list would both mislabel it and bury it at the bottom. `check_vulnerabilities` returns `supply_chain` separately, `get_plugin_details` gives it its own field, and neither is ever paginated or truncated away — there are at most a handful per estate.
    - **Its own flags on `list_plugins`,** `supply_chain_malicious` / `_suspicious` / `_cleaned` / `_undetermined`, separate from `has_vulnerability`. One flag covering both would let the more serious fact hide behind the commoner one.
    - **The three verdicts mean different things and are documented individually** in `get_capabilities`. `cleaned` in particular does not mean safe: it means a clean release followed, and a site still on an affected version is still running the compromised code.
    - **Range semantics differ from a CVE record and the schema says so.** `min_operator` is always `ge`, and a null `max_version` means no clean release exists, so everything from the baseline onward is affected. A CVE record with no upper bound means the opposite — nothing is known. That is why `match_supplychain()` exists rather than reusing `match_record()`; the operator mapping, the `version_compare()` path, and the scalar guards are shared.
    - **`undetermined` is a first-class outcome.** Audits of trunk compromises publish bounds like `trunk@r2268077`, a Subversion revision that no version comparison can resolve — four of the five real audits sampled are of this shape. Such an entry is surfaced with `version_match: undetermined` and a note, never silently dropped and never claimed as a confirmed match. Reporting a hijacked plugin as clean because its range was unparseable would reproduce the exact failure this whole phase exists to prevent.
    - **Indicators of compromise are counted, not listed.** `ioc_count` is the fact a client reasons over; the domains, addresses, and detection rules behind it are the auditor's to publish. `ioc_count: 0` means the audit recorded none, not that the plugin is clean, and `get_capabilities` says so.

58. **MCP revision 2026-07-28 is supported dual-era, decided per request, with nothing dropped.** The revision's headline change — a stateless request/response protocol with no sessions — is the architecture Phase 0 chose, so the migration cost was near zero and the work was additive. Decisions a future agent might reverse:

    - **Era detection is the presence of `io.modelcontextprotocol/protocolVersion` in the request `_meta`, exactly as the spec's dual-era rule states.** A request carrying it is served under 2026-07-28 semantics; anything else takes the legacy `initialize` path unchanged. No state is held about which era a client spoke last time; the same client may alternate eras request by request and each is answered in kind.
    - **Header validation runs before everything else on the modern path, and disagreement is rejected, never resolved.** A body and header that disagree is a request-smuggling shape: `MCP-Protocol-Version` vs `_meta`, `Mcp-Method` vs `method`, `Mcp-Name` vs `params.name` all return `HeaderMismatch` (-32020, HTTP 400), with the Base64 sentinel format decoded before comparison as the spec requires. Missing and mismatched are the same failure.
    - **A modern-shaped request claiming a legacy version is rejected as unsupported, not served legacy-style.** The modern `_meta` keys are undefined in the legacy revisions, so such a request is self-contradictory. The `UnsupportedProtocolVersionError` (-32022) lists every supported version across both eras — the spec's own example lists legacy versions — and the client falls back however suits it.
    - **`ping` and `initialize` return 404/-32601 on the modern path deliberately.** Both are gone from the 2026-07-28 revision (`ping` removed, the handshake retired); answering them under modern `_meta` would be inventing a hybrid protocol nobody specified. They work untouched on the legacy path.
    - **`ttlMs` is 24 hours and `cacheScope` is `private` on tools/list and server/discover.** The tool catalog is fixed at build time and changes only on plugin update, so a long TTL is honest, and a day bounds how long a client can miss a new tool without reconnecting — which retires the reconnect-after-upgrade FAQ for modern clients. `private` because the token rides in the URL path: a shared intermediary caching a secret-addressed response is a leak, whatever the body is. Tool order was already deterministic (glob() sorts), which the revision now recommends for client-side caching.
    - **Deprecated features confirmed absent, each checked individually:** Roots (never implemented), Sampling (never implemented), Logging (`logging/setLevel` never implemented; `notifications/message` never emitted), the HTTP+SSE transport (Phase 0 chose single JSON responses; there is no GET stream and never was), and `Mcp-Session-Id` (never minted, never echoed; the existing 405 on GET already matches the new revision's required response). MRTR, Tasks, subscriptions/listen, and MCP Apps are not implemented: AuditPress makes no server-initiated requests and has nothing to push.

59. **Origin validation: absent passes, present-but-foreign gets 403.** The transport spec's DNS-rebinding guard, previously unimplemented. The direction matters and is easy to get fatally backwards: MCP clients call server-to-server and send no Origin header at all, so an absent Origin MUST be allowed — requiring one would break every legitimate install on day one. Only browsers volunteer the header, and it is exactly browser-borne requests (including the "null" opaque origin, which is rejected) that a rebinding attack arrives under. Present is allowed only for the site's own origin, compared as scheme://host:port with default ports normalized; `auditpress_allowed_origins` filters the list for sites with a legitimate second origin. Rejection is HTTP 403 with a JSON-RPC error carrying no id, the exact shape the spec names. The check runs before rate limiting and authentication: it is the cheapest gate and guards them both.

60. **Origin validation is strict parsing, not tolerant parsing, and compares authorities rather than URLs.** The Phase 9 implementation used `wp_parse_url()` and compared `scheme://host:port`, which the Phase 9.5 audit showed accepted three things it should not have. Recorded so nobody reintroduces the tolerant version:

    - **`https://evil.com@example.com` was allowed.** `parse_url()` reads that host as `example.com` and puts `evil.com` in `user`, so an origin naming the attacker's domain first compared equal to the site's own. Same for `https://a@b@c@example.com`. A path, query, fragment, or trailing slash appended to a valid origin was likewise accepted. The fix is to reject anything that is not exactly a serialized origin — scheme, host, optional port, nothing else — with a regex rather than a URL parser. A browser never sends any other shape, so tolerance bought nothing and cost correctness.
    - **Unparseable values collided.** Every malformed string normalized to `''`, so if a site filtered in an allowed origin that failed to parse (`example.com`, no scheme — an easy mistake), that `''` matched every malformed Origin, including `javascript:alert(1)` and `null`. Now an unparseable value is `null` and matches nothing, on both sides of the comparison.
    - **Scheme equality broke same-origin requests on TLS-terminating proxies.** The development clone records `home_url()` as `http://` while being served over `https://`, so its own browser origin was rejected. Comparison is now by authority (host:port) with the scheme required to be http or https but not required to match, and a site URL without an explicit port contributes both default ports. The host is the boundary a DNS-rebinding attack has to cross; the scheme is not, and demanding it match breaks real deployments while stopping no attack.

    Also: the Origin header is length-capped before parsing, since it is parsed before authentication.

61. **`tools/call` guards the tool name as a scalar before casting.** A `params.name` arriving as a JSON array reached `(string)` and emitted an `Array to string conversion` warning on every request; as an object it raised an uncaught `Error`. The array path was reachable over HTTP on both protocol eras and dated from Phase 0 — `json_decode($body, true)` never produces objects, so the fatal was not reachable over the wire, but the guard covers both. This is the same discipline the enrichment parser applies before `version_compare()` (48): hostile input never reaches a cast that can warn or throw.

    Attacker-supplied values echoed in error messages — the unknown tool name, the unsupported protocol version — are now capped at 64 characters and stripped of control characters. A 10,000-character version string was previously echoed in full. The values are not secret and the responses are JSON rather than HTML, so this is not an injection fix; it is that unbounded attacker text on its way into a model's context is worth bounding, and control characters have no business in a log line.

62. **The rate limiter stops writing once a client is over the limit.** `allow_request()` wrote the bucket transient on every call, including calls it was about to refuse, so a flood against an unauthenticated endpoint bought one database write per request. Once the count reaches the limit inside the window the answer cannot change, so it now refuses without writing.

63. **Verifying a clean error log means finding that stack's log path first, and proving the log would have caught something.** Two different stacks, two different destinations, and neither is the one a developer assumes:

    - **LocalWP (nginx + PHP-FPM):** PHP warnings go to `logs/php/error.log` inside the site folder, *not* `wp-content/debug.log`, which stays empty even with `WP_DEBUG_LOG` on. A check reading `debug.log` here reports clean no matter what happens.
    - **Hostinger (LiteSpeed + CloudLinux):** `log_errors` is off by default and `wp-content/debug.log` does not exist, so nothing is recorded at all. The stack's own files are `public_html/php_errorlog` and `~/.logs/error_log_<domain>`, both of which sat untouched for years. Setting `WP_DEBUG_LOG` does work — WordPress's `ini_set()` takes effect — and then `debug.log` becomes the real destination.

    So an empty log is worthless as evidence on its own: it is equally consistent with "nothing went wrong" and "nothing was being recorded." Any future clean-log claim must fire a deliberate `trigger_error()` canary through the web SAPI first, confirm it lands, and ideally fire it again afterwards to show the log was still live for the whole run. On the live site this produced 60 log lines across 19 tool calls in both protocol eras, every one of them from the site's 2015-era theme (`register_sidebar`, `register_sidebar_widget`) and **none** from this plugin.

64. **The name is Auditra, slug `auditra`. Supersedes 39.** wordpress.org pended the submission: "AuditPress" was rejected as a portmanteau of the WordPress trademark. The reviewer's guidance is explicit that altered forms of a trademark — blend words and portmanteaus included — are not permitted, and that MemberPress and SEOPress exist only because they are grandfathered, with grandfathering explicitly not lasting. Not contestable, and not worth an appeal.

    **The lesson that cost two renames: the Plugin Check restricted-term list is the automated gate, not the trademark guideline, and clearing one does not clear the other.** Decision 39 verified `auditpress` against Plugin Check's own 112-term matcher, found it clear, and called the name final. That check was correct and irrelevant: the restricted-term list catches bare words like `plugin` and `wordpress`, and says nothing about *derived* forms of the trademark. A name can pass every automated gate and still fail human review on trademark grounds. Any future name must clear both, and the trademark rule is the one with no tooling behind it.

    `Auditra` is a coined word rather than a compound of real words, which is the pattern the reviewer's own guidance asks for. Verified before adoption: the wordpress.org slug is unregistered, no plugin in the directory uses it, no software product carries the name, and no registered trademark surfaced. Nothing named `plugin`, `wp`, or `wordpress` appears in the name or slug; "WordPress" appears only in the description and readme body, which are unrestricted.

    The rename covers the display name, slug, text domain, every class/constant/function prefix, all option and transient keys, the REST namespace (`auditra/v1`), the main file, the plugin directory, the repository, and every documentation reference. `pluginlens.local` and `pluginlens-test` are deliberately untouched: they are infrastructure hostnames, not product names, and 45 already records that they never move with the plugin. Option keys were renamed rather than migrated because the plugin has never shipped — there is no installed base to carry forward, and a migration path for zero users is dead code on arrival.

65. **The plugin prints no inline `<script>` or `<style>` tags.** The copy-to-clipboard handler on the connection URL was a raw `<script>` block in admin markup, which wordpress.org flagged. It now rides `wp_add_inline_script()` on a registered handle with `src` of `false`, attached to `admin_print_footer_scripts-{suffix}` for the settings screen alone rather than a global `admin_enqueue_scripts` callback with an internal screen check — the hook itself is the guard, so the script cannot reach another admin page even by mistake. Inline `style` *attributes* on individual elements remain and are not the same finding; core admin markup uses them throughout and Plugin Check does not flag them.

66. **The output buffer is paired to its own nesting level, never torn down wholesale.** wordpress.org flagged the `ob_start()` in `register_routes()` as unbalanced. It was: cleanup ran `while ( ob_get_level() > 0 ) ob_end_clean();`, which closes *every* open buffer — including ones core, the theme, or another plugin opened and still intend to close themselves. Two fixes, both verified by opening a foreign buffer underneath ours and measuring it at the moment cleanup runs:

    - **Close only our own level.** `register_routes()` records `ob_get_level()` after starting, and `discard_buffer()` unwinds only down to that mark. Measured before the fix: a foreign buffer at level 3 was gone (`level_now=0`). After: it survives intact (`level_now=3`) on all four request paths — success, notification, bad token, and unmatched route.
    - **Close on every path out.** Cleanup used to return early when the route did not match, but the buffer is opened from the request URI *before* routing, so a request that never reaches the callback — a token failing the route pattern — left it open for the rest of the request. `discard_buffer()` now runs before that check, is idempotent, and is additionally hooked to `shutdown` at priority 0 as a fallback for a response that never reaches `rest_pre_serve_request` at all.

    Note for anyone measuring this: core hooks `wp_ob_end_flush_all()` to `shutdown` at priority 1, so by any later point every buffer is closed regardless. The meaningful measurement is taken at `rest_pre_serve_request`, where our cleanup actually runs.
